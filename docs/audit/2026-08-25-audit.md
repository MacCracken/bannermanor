# BannerManor — 1.1.4 Security & Hardening Audit

**Date**: 2026-08-25
**Auditor**: maintainer (six parallel review lanes + adversarial verification pass)
**Scope**: all of `src/*.cyr` (2,970 lines) at `1.1.3` + `[Unreleased]`, plus `tests/`, `docs/`, `SECURITY.md`, `README.md`, `scripts/doc-pin-check.sh` and the CI workflows. `lib/` read for parse semantics only; never modified.
**Method**: P(-1) steps 2–6 run as six independent lanes — argv→render input bounds, font-parser validation, output-buffer sizing & write path, optimization/footprint, external research (FIGfont spec + 2026 CVE corpus), and documentation — each reading the source in full and executing every claim against the shipped binary. Every surviving finding was then re-derived by an adversarial verifier that attempted refutation on six grounds (reproducer fails, path unreachable, prior-accepted, style preference, fix breaks the frozen v1.0 output contract, CLAUDE.md hard-rule violation). Six findings were refuted outright and are recorded below so they are not re-derived.

This audit closes the P(-1) hardening pass for `1.1.4`. One HIGH-severity vulnerability (S-001) and one MEDIUM (S-002) are fixed in the same release, along with two MEDIUM correctness/compatibility defects in the `.flf` adapter. Twelve findings are accepted as documented risk; twelve are deferred to filed issues.

---

## Threat model

Unchanged in shape from 2026-05-20, with two corrections and one addition.

bnrmr is a single-shot CLI that:

1. Reads positional argv text (≤ 1 KB). **It does not read stdin** — there is no `read(0, …)` anywhere in `src/`. `SECURITY.md` claimed otherwise; corrected in this release.
2. Reads a font: the in-tree embedded default, `--font NAME` → `fonts/NAME.cyml` (sanitized by `build_font_path`), or `--font path.flf` → a literal path (F-003, still accepted).
3. **Enumerates and reads every `fonts/**/*.cyml` under the process CWD when `--list-fonts` is passed.** This leg was under-weighted in the 0.7.0 model and is where this audit's HIGH finding lives.
4. Reads layout flags, the `--color` flag, `$COLUMNS`, and `TIOCGWINSZ`.
5. Writes banner bytes to stdout and exits.

No daemon, no cache, no network, no shellout, no eval, no signal handlers.

The canonical concern remains **CWE-150 — ANSI escape sequence injection**. The 0.7.0 audit correctly identified this as bnrmr's bug shape and fixed the payload half (F-001, `.flf` glyph rows). What it did not model is that a font file has a *metadata* half, and that `--list-fonts` prints it. The 2026 advisory corpus that has accumulated since is almost entirely metadata-shaped rather than payload-shaped (see §External research), which is exactly why this class survived to 1.1.3.

The friction gradient matters for severity calibration and is the axis the 0.7.0 audit itself used:

| vector | user action required |
|---|---|
| F-001 (`.flf` glyph rows, **HIGH**, fixed 0.7.0) | user names the malicious file: `--font evil.flf` |
| F-003 (`.flf` literal path, LOW, accepted) | user names the path |
| **S-001 / S-002 (this audit, HIGH / MEDIUM)** | **user types `--list-fonts` in an untrusted directory** |

S-001 removes the opt-in gate that the audit's own text cited as what held F-001 below critical (\"Severity is gated by the `--font path.flf` opt-in\"). By that stated reasoning, HIGH is the internally consistent rating. `--list-fonts` also performs no `stdout_is_tty()` check, so unlike the color path (F-006) the bytes reach pipes and logfiles too.

### S-001 — CYML `name` and `description` reach stdout unfiltered  **HIGH**  **FIXED**

Independently reproduced by three lanes with byte-for-byte agreement.

`_font_get_str` (`src/font.cyr:433-505`) locates `key = \"value\"` in a CYML header and copies the value with `memcpy(dst, hdr + start, vlen)` (`:483`). The value scan (`:473-478`) terminates only on `\"` (34) and `\\n` (10). Every other byte — ESC (0x1B), BEL (0x07), CR, NUL, the whole C0/C1 range — is copied verbatim. `font_header_load` stores the result into `name_buf` (`:560`) and `desc_buf` (`:563`). `cmd_list_fonts` then writes both to fd 1 with no filter: `_print_padded(font_hdr_name(h), 10)` (`src/main.cyr:183` → `syscall(1, 1, cstr, n)` at `:142`) and `syscall(1, 1, desc, strlen(desc))` (`:191-192`).

Confirmed payloads, all delivered intact and verified on a real pty under `script(1)` as well as through a pipe: `ESC]0;…BEL` (OSC 0 window-title set), `ESC[21t` (CSI title-report — the Ghostty/xterm command-injection chain), `ESC]8;;…BEL` (OSC 8 hyperlink), `ESC[2J` / `ESC[H` (erase display, cursor home), `ESC[1;31m` and `ESC[8m` (SGR, including conceal), and bare CR (line-overwrite spoofing of the listing). 256 description bytes plus 64 name bytes is ample budget, and multiple font files stack.

Two secondary effects: `_print_padded` computes its column padding from `strlen` (`src/main.cyr:141`), so zero-width sequences corrupt the listing's alignment (a 7-byte `ESC[2Jclr` name gets 3 pad spaces as if 7 columns were visible when only 3 are); and because the value scanner does not stop at byte 0, an embedded NUL silently truncates the printed string via `strlen` while `vlen` counts the full length.

Reachability needs no `--font` opt-in: `cmd_list_fonts` calls `find_files(str_from(\"fonts\"), str_from(\".cyml\"))` (`src/main.cyr:158-160`) against a CWD-relative directory, and `find_files` → `dir_walk` recurses to depth 64, so `fonts/pack/deep/evil.cyml` lists too. Running bnrmr inside an unpacked tarball, a cloned repo, or `/tmp` is sufficient.

This is the metadata half of F-001. The 0.7.0 fix was scoped to `.flf` glyph rows on the stated reasoning that \"the CYML body parser is already restricted to `'.'`/`'#'` so this fix is .flf-specific\" — true of the *body*, and it silently left the *header strings* as the one CYML→stdout byte path that bypasses the `'.'`/`'#'` decoder. F-004 examined `--list-fonts` only to confirm `cyml_expand_value` is not invoked (still true), and F-005 covers only the argv→stdout direction (re-verified: ESC in argv still yields 0 ESC on stdout).

**Fix**: scrub at the parser boundary, in `_font_get_str` (`src/font.cyr:483`), so every current and future consumer of a CYML header string is safe by construction. Shared predicate `_scrub_ctl(b)`, identical to `src/flf.cyr:247-249`: `b < 32 → 32`, `b == 127 → 32`, `b >= 128 && b <= 159 → 32`. Folding NUL into the first arm also resolves the truncation.

**Recorded consequence**: keeping the C1 arm for symmetry with the `.flf` path means UTF-8 continuation bytes in 0x80-0x9F would be rewritten to space in a non-ASCII font name. No shipped font is affected — `fonts/{block,slim,big}.cyml` carry pure printable ASCII in both fields, and their only non-ASCII bytes live in `#` comment lines the header scan never feeds to `_font_get_str` — and ADR 0001 is ASCII-only by charter through v1.0. This is a decision, not an oversight.

**Contract impact**: none. `font_load_file` never reads `name`/`description`, so no rendered banner byte can change. `--list-fonts` output for a normal install is byte-identical (verified: 0 control bytes on stdout today from the repo root). The scrub is length-preserving, so the column math is unchanged.

### S-002 — `--list-fonts` echoes the raw filesystem path on the malformed branch  **MEDIUM**  **FIXED**

`src/main.cyr:177-180` writes `syscall(1, 1, str_data(path_str), str_len(path_str))` before the `(malformed — skipped)` text. The bytes come from `find_files` walking the real directory, so they are whatever the filesystem holds. Reproduced: a file named `ev<ESC>[31mil.cyml` emits `1b 5b 33 31 6d` raw.

This is a **separate** defect from S-001, not a duplicate: this branch fires precisely when `font_header_load` returned 0, so a parser-boundary scrub provably cannot cover it. `build_font_path`'s byte allowlist (`src/main.cyr:52-61`) governs only the `--font NAME` resolution path and is never consulted here.

Payload set is narrower than S-001's — filenames cannot contain `/` or NUL, so an OSC 8 hyperlink with a URL is not expressible — but SGR, CSI 2J/H, OSC 0/2, CSI 21t and bare CR all are.

**Fix**: per-byte write through the same `_scrub_ctl` predicate at `src/main.cyr:179`. Output bytes are identical for every ASCII path, which preserves the `--list-fonts`-with-malformed-fonts case covered by the 79-invocation golden diff recorded for 1.1.3. The \"print only the sanitized basename stem\" alternative was rejected for exactly that reason.

**Credit where due**: every *other* user-echo site is clean. All of `src/main.cyr`'s error messages are string literals — `bnrmr: invalid font name` (`:349`), `bnrmr: failed to load .flf font (missing or malformed)` (`:342`), `bnrmr: failed to load font (missing or malformed)` (`:354`), and the `--color`/`--align` diagnostics (`:303`, `:329-332`) — none interpolate the user-supplied value or path. That is good design and should stay.

### C-001 — `.flf` endmark detected without figlet's trailing-whitespace trim  **MEDIUM**  **FIXED**

figlet's reference `readfontchar()` (figlet.c:1129, fetched and read directly) processes each FIGcharacter line in a fixed order: trim trailing `ISSPACE` **first**, then take the last remaining byte as the endmark, then strip its run. `src/flf.cyr` has no equivalent of the first loop — it strips exactly one trailing CR (`:208-211`, the issue-0003 fix) and then reads `endmark = load8(buf + eff_end - 1)` (`:219`).

Consequence on a spec-conformant font with trailing whitespace after its endmarks: the last byte is a space, `endmark` latches as 32, the strip loop at `:224-231` eats the spaces and stops at the endmark, and the literal `@`/`#` characters render as banner art. A trailing TAB does the same (figlet's `ISSPACE` covers it; `:208-211` checks only 0x0D). The defect is per-row as well as per-glyph: whitespace on any row r>0 leaks that row's endmarks independently of the row-0 latch.

Real-world reach, measured rather than asserted: **0 of 18 upstream figlet fonts** and **7 of 379 xero/figlet-fonts archive fonts (1.8%)** — Calvin S, Georgi16, JS Block Letters, JS Bracket Letters, JS Cursive, Stick Letters, maxiwi. `bnrmr --font \"Stick Letters.flf\" \"AZ[\"` renders literal `@` and `@@` in 4 of 8 rows today.

Not a security issue — the leaked bytes are printable and the F-001 scrub still runs on them — but a fidelity defect in an adapter whose stated purpose (`src/flf.cyr:3-5`) is to let users point `--font` at their existing figlet libraries, and it fails silently rather than rejecting.

**Fix**: extend the `eff_end` walk-back into a loop over {32, 9, 13, 11, 12}. `cursor = line_end + 1` (`:259`) unchanged.

**Contract impact — output-byte change, bounded and measured.** A 397-font differential (18 upstream + 376 archive + all in-tree fixtures + `modular.flf`, 991 comparisons) yields **8 differing glyph sets across exactly 7 fonts — all 7 already misparse today, and no font changes its load/reject status.** `tiny.flf`, `flf_crlf.flf`, `flf_esc_glyph.flf` and `modular.flf` contain zero lines ending in space/TAB, so `t_load_tiny_flf` and `t_flf_crlf_endmarks_stripped` are no-ops under the new loop.

**Divergence recorded**: figlet does NOT reject an all-whitespace row — its `k<0` branch stores an empty row and continues. bnrmr's existing `llen <= 0` rejection at `:213` is kept as a knowing divergence; 0 of 397 corpus fonts contain a whitespace-only glyph row, so it is measured-safe, but it must not be described as figlet-matching.

### P-001 — `.flf` hardblank restricted to 33..126  **MEDIUM**  **FIXED**

`src/flf.cyr:129-131` rejects any hardblank `< 33` or `> 126`. The FIGfont spec allows any byte except NUL, LF, CR and space, and explicitly *recommends* DEL (0x7F): \"If you want the entire printable ASCII set available to use, make the hardblank a 'delete' character.\" figlet parses it with a bare `%c` (figlet.c:1210-1212) and applies no range check at all.

Measured against the 1052-font cmatsuoka/figlet-fonts corpus: **17 fonts (1.6%) are rejected**, including `bubble.flf`, `digital.flf` and `term.flf` — three of the 18 fonts in the canonical figlet distribution — plus doh, alphabet, cards, rot13, B1FF, pyramid (0x81). Byte 5 alone is the barrier: rewriting it to a printable byte makes all of them load and render correctly.

Compounding this, the comment at `src/flf.cyr:239-241` — the rationale text for F-001, the project's only HIGH historical finding — asserts \"Hardblank is substituted before this filter, so legitimate hardblank=0x01 fonts still work.\" That was false: the `:130` guard rejected such a font 110 lines earlier, so the path was dead. Anyone reading the F-001 fix believed in a code path that did not exist.

**Fix**: reject only `hardblank == 0 || 32 || 10 || 13`, and correct the comment. Safe because the hardblank→space substitution at `:246` already precedes the F-001 scrub at `:247-249`, so a DEL or C1 hardblank becomes 32 and never reaches stdout. This strictly **widens** what loads — no currently-working font can change bytes, because a hardblank in 33..126 takes an identical path either way.

### S-003 — `$COLUMNS` bypasses both width caps  **LOW**  **FIXED**

F-008's recommendation (\"cap `ws_col` at 4096\") was implemented at `src/layout.cyr:101`, and issue 0002 capped `--width` at 4096 in `src/main.cyr:312-315` explicitly \"to match the F-008 `WS_COL_CAP`.\" The third frame source got neither. `term_width_env` (`src/layout.cyr:127-133`) returns whatever `parse_uint` accepts, ceilinged only by `PARSER_INT_CAP = 1048576` — 256× the cap the same file declares for the same quantity, and the `LayoutLimits` comment at `:30-41` asserts a symmetry the third source silently breaks.

Measured: `COLUMNS=1048576 bnrmr --align right \"A\"` → 5,242,885 bytes via ~5.24M one-byte `write(2)` calls. `COLUMNS=1048577` → 405 bytes (rejected by `PARSER_INT_CAP`, confirming that is the only guard). `COLUMNS=5000` → a 5,001-byte first row, exceeding both documented caps. Reachability requires `--align center|right` (with left align and no `--width`, `frame` stays 0) and non-TTY stdout.

F-002 did trace `$COLUMNS`, but only the *truncation* half — \"a still-positive huge value flows into `fit_chars`, where the `n > len → return len` clamp pins the glyph count\" — which remains correct and is why there is no allocation blow-up. The *alignment* half (`align_pad` → `_write_spaces`) was never traced, and `align_pad` has no such clamp.

**Severity is LOW, deliberately.** F-008 rated the identical clamp on the identical quantity as LOW/ACCEPTED, and issue 0002 assessed the byte-for-byte equivalent amplification reached via `--width` under a heading literally titled \"Why this isn't a security issue,\" classing it \"cosmetic / user-DoS-of-self.\" The escalation argument (\"the environment is inherited from cron/CI/sudo/systemd\") does not survive checking: neither bash nor zsh exports `COLUMNS` (`env | grep -c COLUMNS` → 0 in both), sudo's `env_reset` strips it, and sshd's default `AcceptEnv` does not carry it — those are the contexts where COLUMNS is *absent*, which is why the 80-column fallback exists. bnrmr is not setuid; env and argv share one trust boundary. What genuinely stands is the **consistency defect**, and that is how it is filed.

**Portability note, which is the real reason to fix it now**: on AGNOS, `term_width_ioctl` is `#ifdef CYRIUS_TARGET_AGNOS → return 0`, so `$COLUMNS` is the *only* frame source and `WS_COL_CAP` never executes at all.

**Fix**: clamp in `term_width_env`, not in `resolve_frame` — the latter also covers the explicit `requested > 0` branch and would silently override a future raised `WIDTH_CAP`. **Output-byte change** confined to `COLUMNS > 4096` + center/right + non-TTY; `grep -rn COLUMNS tests/` returns nothing and `--help` documents no COLUMNS ceiling, so this is `Changed`, not `Breaking`.

### B-001 — `--width` / `--pad` accept i64 modular wraparound  **LOW**  **FIXED**

F-002 capped all three of bnrmr's hand-written integer parsers at `PARSER_INT_CAP`. It did not cover the fourth parser in the argv path: `_flags_parse_int` (`lib/flags.cyr:225-245`) accumulates `n = n * 10 + (c - 48)` with no guard and no digit limit. `src/main.cyr:271-272` registers both numeric flags through it and then validates only the **post-wrap** residue at `:307-324`.

Verified: `--pad 18446744073709551617` renders with pad=1 (7 lines), `--pad 18446744073709551626` with pad=10 (25 lines), `--pad 36893488147419103232` with pad=0, `--width 18446744073709551620` emits five bare newlines — all exit 0 with no diagnostic, while `--pad 65` and `--width 4097` correctly reject. F-002's reasoning (\"an overflowed parse becomes a negative number, which the `<= 0` check catches\") covers only residues in the negative half; it is a coin flip and the input picks the half.

Not memory-unsafe — the accepted residue is always a legal in-cap value, so no allocation or output volume is driven by it — but it silently violates the contract issue 0002 froze at v1.0. Filed as a **contract-conformance defect on a closed issue**, not a security bug: argv is trusted by bnrmr's own threat model, and anyone able to inject argv can pass `--pad 10` directly.

**Fix**: `flags_add_str` + `parse_uint` in `src/main.cyr`, since `lib/flags.cyr` is off-limits. Two behaviours must be preserved exactly: `--width -0` / `--pad -0` are **accepted today** (`_flags_parse_int` returns `0 - 0 == 0`, which passes the `< 0` guard) and must remain so; and an all-digit token above `PARSER_INT_CAP` must still print the `max` message, not `bad integer value`. `--width +5` and `--width \" 5\"` stay on their current `bad integer value` path. **Exit-code change** only for inputs currently accepted by wrapping.

### S-004 — FIFO in the font path blocks bnrmr forever  **LOW**  **FIXED (2 of 3 sites)**

All three font readers open with `file_open(path, 0, 0)` — O_RDONLY, no O_NONBLOCK, no file-type check — and the read loops terminate only on `n <= 0` or the size cap. On a FIFO that blocks in `open(2)` until a writer appears, and again in `read(2)` if a writer is attached but idle.

F-003 accepted the `--font foo.flf` literal-path risk partly on the grounds that \"`flf_load_file` validates `flf2a$` magic before allocating any glyph storage.\" That argument does not survive here: the block happens *before* any magic check.

Two in-src sites, both reproduced at rc=124 under `timeout`:
- `src/font.cyr:356` — `--font hang` where `fonts/hang.cyml` is a FIFO. `build_font_path` correctly prevents escaping `fonts/` but cannot police what an attacker puts *inside* it. Confirmed to be a pure blocking issue, not a rejection: with a writer attached feeding `slim.cyml` content, the same command renders and exits 0.
- `src/flf.cyr:43` — the `.flf` literal path; with an idle writer the block moves into `read(2)`.

Everything else in this class is fine and was probed: a directory, `/dev/null`, `/dev/zero` (terminates at the 1 MB cap in ~1 ms), `/dev/urandom`, `/proc/self/mem`, `/proc/self/environ`, a renamed `/etc/passwd`, and `../../../` traversal all exit 1 within milliseconds.

**Fix**: path-based `xstat` + `S_ISREG` gate before the read loop at both sites, using the idiom `lib/io.cyr:236-247` documents. `xstat` (lib/io.cyr:370) and `STAT_MODE` are already target-bridged for x86_64-linux, aarch64-linux and agnos, so no raw syscall and no `#ifdef` is needed — which is why this is preferable to the O_NONBLOCK alternative (that would silently convert a legitimately-slow regular-file read into a load error on any target where a short read can return `-EAGAIN`).

**Third site NOT fixed — see accepted risk A-08.** The `--list-fonts` hang is not at `font_header_load`; it is at `lib/fs.cyr:367`, in `is_dir`'s blocking `sys_open`, invoked once per directory entry by `dir_walk`. Proven twice: a FIFO named `fonts/notafont.txt` — filtered out by the extension check and therefore never passed to `font_header_load` — hangs identically, and the hung process emits zero bytes, not even the `Available fonts (fonts/):` header. Fixing it would require bnrmr to stop using `find_files` and do its own `getdents64` d_type enumeration; filed upstream instead.

### C-002 — `ws_col == 0` makes the two TIOCGWINSZ probes disagree  **INFORMATIONAL**  **FIXED**

`term_width_ioctl` (`src/layout.cyr:88-104`) treats `cols <= 0` as failure and returns 0; `stdout_is_tty` (`:110-124`) checks only `r == 0` and reports 1. On a TTY reporting `ws_col == 0` — a fresh pty before `TIOCSWINSZ`, some serial consoles, detached-session ptys — `render_layout` takes the *pipe* branch for width (`clamp_w = 0`, so issue 0004's narrow-terminal wrap protection is silently disabled) while taking the *tty* branch for color. That is the exact combination issue 0004 was filed to prevent. Verified on a real pty at cols=0: 405 bytes at the 80-column fallback, with 10 escape sequences emitted. `ws_col == 1` is handled sanely (0 glyphs, 1 space per row).

**Fix**: have `stdout_is_tty` apply the same `cols > 0` test, ideally by factoring a single `_winsize_cols()` both build on — which also removes a duplicate ioctl (three `TIOCGWINSZ` calls can fire on fd 1 in one colored render). AGNOS `#ifdef` branches unchanged.

### R-001 / R-002 — two zero-risk hygiene fixes  **INFORMATIONAL**  **FIXED**

`block_font_embed` (`src/font_block.cyr:629`) discards `font_set_char`'s return, which signals both out-of-range and **duplicate** chars. If `_block_glyph_char` ever mapped two indices to the same ASCII byte, the second glyph would be silently unreachable. Verified clean today — the seven arithmetic ranges are disjoint, all 347 row literals are exactly 5 bytes of `' '`/`'#'`, the embedded font renders byte-identically to `fonts/block.cyml`, and all 95 printable ASCII chars render non-blank — but the table is hand-maintained across two files under an explicit drift discipline, which is exactly where a silent failure eventually costs an afternoon. The CYML loader (`src/font.cyr:415`) and the `.flf` loader (`src/flf.cyr:275`) both check this return; only the embedded path drops it.

`lens_scratch` (`src/flf.cyr:186-187`, written at `:253`) is allocated (up to 24,320 bytes), null-checked, written once per row, and **never read** — residue from the abandoned variable-width plan noted at `:9-12`. It costs an allocation, a store per row, and a failure path that can reject an otherwise-valid font for a buffer nothing needs.

## External research summary

Survey period: 2026-05-20 → 2026-08-25. Two categories moved.

**A. ANSI escape injection has shifted from payload to metadata.** The 0.7.0 survey modelled fonts as payload, which is why F-001 was scoped to glyph rows. Every close-shape advisory since has been *untrusted metadata rendered into a human-readable listing*:

- **CVE-2026-44972** (GuardDog) — \"Unsanitized human-readable scan output allows terminal escape injection from malicious package content.\"
- **CVE-2026-54162** (Ember) — unneutralized terminal escape/control sequences from Caddy logs injected into the operator's TUI.
- **GHSA-4hmj-39m8-jwc7** (OpenClaw, ≥2026.2.13 <2026.3.28, CWE-116 + CWE-150) — tool *titles* carried ANSI into approval prompts and permission logs.
- **CVE-2026-45803** (GitHub CLI, `gh run view --log`) — the shape the 0.7.0 audit already cited, recurring.
- vercel-labs skills CLI ANSI escape injection (Seal Security writeup).

`--list-fonts` is precisely this shape: a listing that prints a name and a description supplied by a file the user did not author. S-001 and S-002 are the direct consequence.

Weaponizability of the observed payloads is established, not hypothetical: Ghostty ≤ 1.0.0 turned `ESC]0;<cmd>BEL` plus a title-report request into arbitrary command execution — the same class as CVE-2003-0063 / CVE-2008-2383 already cited in the 0.7.0 audit. The *guaranteed* impact without a vulnerable emulator is output spoofing (`ESC[8m` concealing the real font name, OSC 8 hyperlink deception, `ESC[2J`/`ESC[H` erasing prior context, bare CR overwriting a listing line) plus log injection on the ungated non-TTY path.

**B. FIGfont conformance.** `src/flf.cyr` was diffed field-by-field against `figfont.txt` and against figlet's own `readfontchar()`/header `sscanf`. Two reproducible misparses (C-001, and the per-line endmark divergence recorded as A-03) and one over-strictness (P-001) were found. Notably, the reference implementation is *looser* than bnrmr almost everywhere: it never reads Baseline into a variable (`%*d`), masks rather than range-checks Old_Layout, clamps out-of-range geometry instead of rejecting, and adds 100 bytes of slack to `maxlen` because it does not trust the declared value. Attempts to make bnrmr *stricter* against the spec text were measured against a 1052-font corpus and rejected as net regressions (A-02).

**C. Terminal-size trust.** F-008's clamp was implemented but only on the ioctl leg (S-003). No new CVE class here; the finding is internal consistency plus the AGNOS portability consequence.

**D. Billion-laughs / expansion.** Still not reachable. `cyml_expand_value` has zero callers in `src/` (re-grepped). F-004's policy — *never call `cyml_expand_value` from the font loader* — holds and should be restated in the ADR.

**E. Fuzzing.** No external finding, but recorded: the 0.7.0 \"stand up `tests/bannermanor.fcyr`\" item is still a stub. 7,000 ad-hoc mutation iterations run during this audit (all 8 fixtures + block.cyml, both parsers, structure-aware C0/C1 and endmark-byte injection) produced zero crashes, zero hangs, zero out-of-range exit codes and zero control bytes on stdout — so the memory-safety posture is good, and the honest conclusion is that a crash-oracle fuzzer would not have found S-001, C-001 or the endmark divergence. Those need an oracle written by someone who already knows the defect. See issue 0010.

## Accepted-risk register

Following the 2026-05-20 convention: these are **decisions**, not oversights. Revisit only if the stated rationale changes.

| ID | Risk | Rationale |
|---|---|---|
| **A-01** | `--font path.flf` accepts literal paths (F-003, carried forward) | All four supports re-verified at 1.1.3: user types the path; magic checked before glyph alloc; 1 MB cap; F-001 scrub in place. Documentation debt discharged in 1.1.4. |
| **A-02** | `.flf` Baseline / Max_Length / Old_Layout / Print_Direction / Full_Layout / Codetag_Count unvalidated | Enforcement measured as a net regression: `max_width + 2 > max_len` rejects 38 of 950 working corpus fonts (bnrmr's `max_width` is a byte count, Max_Length is character-oriented — dimensionally wrong for UTF-8 box-drawing fonts); `baseline` range rejects 4 more plus **three in-tree fixtures including `flf_esc_glyph.flf`, the F-001 regression fixture**. figlet enforces none of it. |
| **A-03** | `.flf` endmark latched per-glyph, not per-line | 376-font differential: per-line detection changes 7 fonts and corrects **0**. C-001's whitespace trim alone reaches exact figlet parity on all 376 fonts / 35,720 glyphs. Comment corrected; code unchanged. |
| **A-04** | `.flf` C1 scrub can split a UTF-8 sequence, leaving an orphan lead byte | Not an F-001 bypass — the opposite: the scrub defeats UTF-8-encoded-C1 attacks because the continuation byte is itself scrubbed. Extending to 0xC0-0xFF would turn Latin-1/CP437 box-drawing fonts from mojibake to blanks. Documented instead. |
| **A-05** | Sub-glyph `--width` emits `height` blank rows, not \"nothing\" | Changing it alters output bytes for every `--width` below one glyph and every terminal narrower than one glyph — frozen contract. Three doc sites corrected instead. |
| **A-06** | `--color=` silently means \"no color\" where `--align=` errors | Harmonising moves a currently-exit-0 invocation to exit 1 on a v1.0-frozen flag surface, for a cosmetic asymmetry with no security consequence. Revisit at 2.0. |
| **A-07** | `render_layout`'s return is discarded at `src/main.cyr:383` | All three failure returns are provably unreachable from `main` (input bounded to [1,1024]; every font branch already rejects 0). Plumbing for the deferred write-error work, not a live defect. |
| **A-08** | `--list-fonts` hangs on a FIFO under `fonts/` | Blocking site is `lib/fs.cyr:367`, in vendored stdlib that CLAUDE.md forbids editing. Replacing `find_files` with in-tree `getdents64` enumeration far exceeds a patch release. Interruptible self-DoS requiring an attacker-writable CWD. Filed upstream. |
| **A-09** | `font_header_load` never frees its 64 KB read buffer | ~64 KB of never-reused bump allocation per font file (≈67 KB/font RSS on a THP=always host; materially less under 4 KB pages). Shipped tree has three fonts. Graceful growth, no failure, no wrong output at any N. Deferred as a fix, not a security item. |
| **A-10** | 17 write sites hard-code syscall number 1 | Correct on all three targets — x86_64 and AGNOS both define SYS_WRITE=1 with identical argument order, and aarch64's inline ESYSXLAT chain translates literal 1 → 64 (confirmed by disassembly and byte-identical qemu output). Normalize with the deferred `_emit` work: one site instead of 17. |
| **A-11** | `name` is never compared to the filename stem | Enforcement would reject third-party fonts that list today — a `Breaking` change. `--list-fonts` can therefore advertise a name `--font` refuses. Docs corrected to describe reality; enforcement deferred to 1.2.0. |
| **A-12** | `--list-fonts` recurses and lists fonts `--font` cannot load | `find_files` walks to depth 64 while `build_font_path` rejects `/`. Filtering changes listing output for nested installs; pairs with A-11's deferred work. Note: this widens S-001/S-002's reach — a hostile pack need not sit at `fonts/evil.cyml`. |

## Refuted findings (recorded so they are not re-derived)

Six candidate findings were raised and did not survive verification:

1. **\"Every geometry limit constant is dead, therefore the .flf row-width guard is an overflow hazard.\"** The constants are indeed unreferenced, but every one equals the literal it would replace, `src/flf.cyr:266`'s `max_width > 64` is provably unreachable (bounded by the per-row `llen > 64` check), and a 64-column vs 65-column .flf pair confirms the stride guard fires exactly at the boundary. Code hygiene, not bounds — deferred as issue 0012.
2. **\"The fuzz stub means the 1.1.4 hardening claim is false.\"** `cyrius fuzz` appears exactly once in the CHANGELOG, in the shipped **1.1.3** block; the `[Unreleased]` notes make no fuzz claim. And \"fuzz green\" is literally true — a weak signal reported accurately. Re-filed honestly as issue 0010.
3. **\"All three readers treat a `file_read` error as EOF, so a partial read parses as complete.\"** Mechanism is real; impact is not. No reproducer exists (no signal handlers → EINTR unreachable; a pty slave returns n=0 not -EIO; EISDIR is caught by `total <= 0`). A mid-entry truncation is **rejected** by `_font_decode_body`; only a byte-exact entry-boundary truncation loads short, and the result — blank glyphs for uncovered codepoints — is the documented render contract. `t_reader_dir_path` was added in the 1.1.3 cycle specifically to cover this.
4. **\"`--list-fonts` / `--help` syscall counts are a defect.\"** The proposed fix cannot be implemented as described: `fmt_int` lives in `lib/fmt.cyr` and writes directly to fd 1, interleaved between the pieces to be batched, so buffering the literals around it **reorders every geometry digit**. Also: 92% of `--list-fonts`' overhead is the three `font_header_load` calls, not the writes.
5. **\"`.flf` header fields outside spec-legal ranges should be rejected.\"** See A-02 — measured as a 42-font, 3-fixture regression against a spec the reference implementation does not itself enforce.
6. **\"`--align` accepts seven spellings documented nowhere; `centre` appears in no document.\"** It does — CHANGELOG.md:402-404 documents all seven. Every value listed by every doc works; no reader is misled into a failure.

## Documentation findings

Twenty-two documentation defects were found. **The substantive ones are
fixed in 1.1.4** — listed below with their status; the remainder (mostly
wording precision in `fonts.md` and ADR 0001 around the entry cap, the
size-gate boundary, and the two loaders' differing validation) are filed
for a follow-up documentation pass rather than rushed into a hardening
release.

- **FIXED — SECURITY.md** claimed \"fonts that include literal escapes in glyph data are rejected at parse time.\" False twice over: `.flf` glyph rows are **sanitized and loaded**, not rejected, and metadata escapes were neither. (Correctly true for the CYML *body*, where any byte other than `'.'`/`'#'` fails the load.) It also described bnrmr as a \"stdin / argument-input\" renderer; bnrmr never reads fd 0.
- **FIXED (`--help`) / DEFERRED (module comments)** — claimed a sub-glyph `--width` renders \"nothing\" (A-05).
- **FIXED — `state.md`** — the live snapshot that CLAUDE.md declares is refreshed every release — silently skipped releases **1.1.0 and 1.1.1**, never recorded AGNOS as a build target, and cross-referenced \"broken since AGNOS became a target at 1.1.0\" against a log entry that does not exist. `1.1.0` appears exactly once in the entire tree outside CHANGELOG.
- **DEFERRED — `fonts.md` / ADR 0001** documented `name` as required and stem-matching (neither is enforced on the render path), presented one loader-validation list for two loaders with different gates, omitted the zero-entry rejection, overstated the entry cap as 256 when the 128-wide charmap makes 128 the reachable maximum, and stated the size gate as \"exceeds 64 KB\" when the code rejects at `>= 65536`.
- **FIXED (`--help`) / DEFERRED (`--color` error text, `src/color.cyr` comment)** — both omit the accepted `bright-<name>` dash aliases; `--help` also omits `black`, which the error text lists; and `src/color.cyr:44-45` claims a separator-less `brightX` form that does not exist and exits 1.
- **FIXED — `tests/bannermanor.bcyr` and `docs/benchmarks.md`** asserted the write side is \"bounded by terminal/pipe throughput, not bnrmr's code.\" It is bnrmr's code: 28,637 `write(2)` calls to emit 28,679 bytes.
- **FIXED — `docs/benchmarks.md` Point 4's A/B table was invalid** — both `cyrius bench` and `cyrius build` silently restore `lib/bayan.cyr` from the lockfile before compiling (md5 `ce3f7331` in, `17bb46bf` out, reproduced twice), so it compared the current bayan against itself. Its \"the 1.1.3 dep bump is bench-flat\" conclusion is unsupported. Point 1's \"Notes on B2\" attributes the cost to `_font_get_int`, which is wrong by an order of magnitude (3.5-5% vs bayan's 62-65%).
- **FIXED — `docs/adr/README.md`** said \"No ADRs yet\" while ADR 0001 exists and is Accepted — and instructs the next author to create a colliding `0001-`, against the file's own \"never renumber\" rule.
- **NOTED (by design) — `scripts/doc-pin-check.sh`** passes green while README and getting-started both carry a stale assertion count and state.md is missing two releases. Its scope is deliberate and documented (three version-shaped pins over four files); recorded here so the gate is not mistaken for broader coverage.

## Addendum — a measurement-methodology defect in `docs/benchmarks.md`

Found during this audit and worth recording separately, because it
invalidated a published conclusion rather than a line of code.

Point 4 of `docs/benchmarks.md`, written at 1.1.3, claimed "the 1.1.3
dep bump is bench-flat" on the strength of an A/B that swapped the
vendored `lib/` between runs. **`cyrius bench` and `cyrius build` run
dep resolution first and restore any `lib/` file whose hash does not
match `cyrius.lock`** — including stdlib modules, and including with
`--no-deps`. Both rows of that table therefore compiled against the
same bayan. Reproduced directly:

```
$ cp <bayan-1.0.1> lib/bayan.cyr && md5sum lib/bayan.cyr
ce3f7331…  lib/bayan.cyr        # 1.0.1
$ cyrius bench … >/dev/null && md5sum lib/bayan.cyr
17bb46bf…  lib/bayan.cyr        # 1.5.2 — silently restored
```

Re-run correctly — by pointing `CYRIUS_HOME` at a snapshot whose
`lib/bayan.cyr` is the version under test, so the restore reinstates
the intended library — the result reverses:

| `lib/bayan.cyr` | `font_load_file(block.cyml)`, 3 runs |
|-----------------|---------------------------------------|
| 1.0.1 (through 1.1.2) | 59.1 / 58.8 / 61.6 µs |
| 1.5.2 (at 1.1.3)      | 86.2 / 85.5 / 87.0 µs |

**bayan 1.5.2 costs ~27 µs, a ~45% regression**, introduced by the
1.1.3 toolchain bump. The 1.0.1 figure also sits within noise of the
58 µs recorded at Point 3 on cyrius 6.0.1, which retires the
"gradual drift across 6.0.1 → 6.2.24" narrative Point 4 also
published: B2 was flat for three toolchain generations and then
stepped once.

Corrected in `docs/benchmarks.md` at 1.1.4. Root cause inside bayan is
not diagnosed and is deferred; the CYML parse is 62–65% of B2, so it
is the only part worth profiling.

**Process lesson for future dep bumps**: an A/B over vendored `lib/`
is not valid unless dep resolution is neutralised. Swapping the files
and re-running a cyrius command silently measures the same library
twice.
