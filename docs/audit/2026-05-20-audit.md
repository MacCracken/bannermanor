# BannerManor — 0.7.0 Security Audit

**Date**: 2026-05-20
**Auditor**: maintainer (with external CVE survey)
**Scope**: all of `src/*.cyr` at commit `fdec71e` (post-M6 / pre-0.7.0)
**Method**: line-by-line internal review against the P(-1) checklist in
CLAUDE.md (input bounds, font-parser validation, output buffer sizing),
plus external survey of CVEs and attack patterns in adjacent tooling
(figlet, .flf parsers, ANSI escape injection, hand-written text-format
parsers, terminal-size trust, CLI argv→stdout).

This audit closes the **M7 hardening** roadmap item and ships as
`0.7.0`. One concrete vulnerability (F-001) is fixed in the same
release; the remaining findings are either positive observations or
defense-in-depth recommendations for v1.0.

## Threat model

bnrmr is a single-shot CLI that:

1. Reads positional argv text (≤ 1 KB)
2. Reads a font (in-tree default, or `--font NAME` → `fonts/NAME.cyml`,
   or `--font path.flf` → legacy figlet file)
3. Reads layout flags + `--color` flag
4. Writes banner bytes to stdout
5. Exits

No daemon, no cache, no network, no shellout, no eval. The attack
surface is: (a) what an attacker can put into argv text or the font
file, and (b) what bytes reach the terminal.

The canonical concern is **CWE-150 — ANSI escape sequence injection**.
A CLI that funnels untrusted bytes to a TTY can deliver malicious escape
sequences (DECRQSS title-report attacks, OSC 9;9 RCE on Windows
Terminal, OSC 8 hyperlink abuse in pagers). The most direct precedent
is the OpenAI Codex CLI ANSI injection RCE (Feb 2026) and the
`gh run view --log` class of bugs — both share bnrmr's shape exactly.

## Findings

### F-001 — `.flf` glyph rows can smuggle ANSI control bytes &nbsp; **HIGH** &nbsp; **FIXED in 0.7.0**

`src/flf.cyr` parses figlet `.flf` files into the same `Font*` shape as
the CYML loader. The per-byte glyph-row copy at the pre-fix
`flf_load_file` (lines 218–226) substituted hardblank → space but
otherwise wrote the file's bytes verbatim into the row buffer. A
malicious `.flf` could embed an ESC (`0x1B`) or other C0/C1 control
byte inside a glyph row; when the user later ran `bnrmr --font
evil.flf "X"`, the row bytes were written directly to stdout, emitting
real ANSI to the terminal.

Severity is gated by the `--font path.flf` opt-in (the user is naming
the file), but the failure mode matches the documented CWE-150 /
ANSI-injection precedent in §B of the external survey: DECRQSS
title-report on xterm, mintty, iTerm2, SwiftTerm; OSC 9;9 RCE on
Windows Terminal; OSC 8 hyperlink abuse under `less`. The `gh run
view --log` and OpenAI Codex CLI bugs are the closest shape to
bnrmr's.

**Fix**: in the glyph-row copy, after the existing `b == hardblank →
b = 32` substitution, replace any control byte (`b < 32`, `b == 127`,
or `b >= 128 && b <= 159`) with space (32). The CYML body parser is
already restricted to `'.'` / `'#'` so this fix is .flf-specific.

**Test**: `tests/fixtures/flf_esc_glyph.flf` ships an ESC in the space
glyph; `t_flf_strips_control_bytes` asserts the row byte loads as 32,
not 27.

**Files**: `src/flf.cyr`, `tests/bannermanor.tcyr`,
`tests/fixtures/flf_esc_glyph.flf`.

### F-002 — Hand-written integer parsers have no overflow guard &nbsp; **LOW** &nbsp; **ACCEPTED**

`parse_uint` (layout.cyr), `_font_get_int` (font.cyr), and
`_flf_take_int` (flf.cyr) all accumulate `n = n*10 + digit` with no
i64 overflow check. A pathological input like `width = 99999999999999999999`
in a `.cyml` header or a 20-digit `COLUMNS` env value will wrap.

**Why not patched**: every downstream consumer applies a tight bound
*after* the parser returns:

- `font_load_file` rejects `width <= 0 || width > 64`, `height <= 0
  || height > 32`, `gap < 0 || gap > 16`, `count <= 0 || count > 256`.
  An overflowed parse becomes a negative number, which the `<= 0` check
  catches. A still-positive overflow exceeds the `> 64` (etc.) cap.
- `flf_load_file` applies identical caps (`height > 32`, `comments > 1024`).
- `parse_uint` from `$COLUMNS` feeds `resolve_frame`, where `if (w > 0)`
  ignores negative overflow values. A still-positive huge value flows
  into `fit_chars`, where the `n > len → return len` clamp pins the
  glyph count at the input length (≤ 1024) — no allocation depends on
  the parsed value.

The path is safe *by accident of the downstream bounds*. A future
relaxation of any cap could resurface this. Defense-in-depth
recommendation for v1.0: cap the parsers themselves at `1 << 20` and
return `-1` above the cap.

### F-003 — `--font foo.flf` accepts literal paths by design &nbsp; **LOW** &nbsp; **DOCUMENTED**

`_is_flf_path` (main.cyr) routes any `--font` value ending in `.flf`
through `flf_load_file(name)` without `build_font_path`-style
sanitization. The user can pass `/etc/passwd.flf` or
`../../../../tmp/foo.flf`.

**Why this is OK**:

1. The user explicitly types the path — there is no privilege
   escalation, no remote injection vector.
2. `flf_load_file` validates `flf2a$` magic before allocating any
   glyph storage; a non-flf file fails immediately.
3. 1 MB file cap bounds memory.
4. F-001's fix removes the only post-validation byte-injection vector.

The `--font NAME` (no extension) branch *does* sanitize: rejects
`/`, `\`, `.`, control bytes, DEL, and lengths > 64 in `build_font_path`,
so it cannot escape the `fonts/` directory.

Recommendation for v1.0: keep this dual-mode and document explicitly
in the manpage that `.flf` is "literal-path opt-in." No code change.

### F-004 — CYML `${file:}` / `${env:}` expansion is *not* invoked &nbsp; **INFORMATIONAL** &nbsp; **KEEP THAT WAY**

`lib/cyml.cyr` exposes `cyml_expand_value` (lines 339–375) for
resolving `${file:PATH}` and `${env:NAME}` references in string
values. bnrmr's font loader uses only `_font_get_int`,
`_font_get_char`, and `_font_get_str` (in `src/font.cyr`) — none call
`cyml_expand_value`. Strings are parsed verbatim.

**Implication**: a malicious font with `description = "${file:/etc/passwd}"`
renders as the literal string in `--list-fonts` output, *not* the
file contents. Good.

**Future risk**: if a maintainer ever adds expansion to bnrmr's
loaders, they unlock arbitrary file reads through font files. The
expansion itself is non-recursive (`_cyml_read_file_trimmed` reads
into a 4 KB local buffer and returns the bytes without re-parsing),
so billion-laughs is not reachable — but arbitrary file disclosure
is. Document the policy: **never call `cyml_expand_value` from the
font loader.**

### F-005 — Positional argv text bytes never reach stdout directly &nbsp; **POSITIVE OBSERVATION**

The render path in `render_layout` (layout.cyr lines 238–252) uses each
input byte only as an index into the font's 128-byte charmap via
`font_glyph_index`. The bytes that *write* to stdout are the font's
glyph row data, never the user's input. Control bytes (ESC, CSI, etc.)
in argv text are mapped via the charmap → fall back to the space glyph
→ rendered as the font's space-row data → safe.

This closes the entire CWE-150 / ANSI-injection class from the argv
side. The remaining vector was F-001 (font-side), now fixed.

### F-006 — Color suppressed on non-TTY stdout &nbsp; **POSITIVE OBSERVATION**

`render_layout` (lines 222–224) probes `stdout_is_tty()` (TIOCGWINSZ
on fd 1) and emits SGR only when stdout is a TTY. Piping `bnrmr
--color cyan` into `cat`, `less`, or a logfile produces plain bytes.
This kills log-injection-via-ANSI as a downstream concern (CVE-2022-46663
on `less` and similar would only apply if our color output reached
those tools, which it doesn't).

### F-007 — All SGR emission routes through darshana &nbsp; **POSITIVE OBSERVATION**

CLAUDE.md hard-constraint: "no raw ANSI escape codes in the codebase."
`src/color.cyr` only maps user-facing color names to SGR codes; the
actual escape emission is `tty_sgr` / `tty_sgr_reset` from
`lib/darshana.cyr`. bnrmr's audit surface for malformed escape
sequences is therefore the darshana audit surface — a single shared
dependency, not 8 inline escape sites.

### F-008 — `TIOCGWINSZ ws_col` is used only for layout math &nbsp; **LOW** &nbsp; **ACCEPTED**

`term_width_ioctl` reads `ws.ws_col` as a `u16` (max 65535). The value
feeds `resolve_frame` → `fit_chars`, which clamps the resulting glyph
count at `len` (≤ 1024). No allocation is sized from the cols value.
A `resize -s 65535 65535` attack (recommended in the external survey
as defense-in-depth) cannot trigger overflow or OOM here.

For v1.0 defense-in-depth: cap `ws_col` at 4096 inside
`term_width_ioctl`. Cheap, optional.

### F-009 — Output buffer sizing is bounded at every level &nbsp; **POSITIVE OBSERVATION**

- argv text capped at 1024 bytes (`join_positionals` rejects overflow).
- `cyml` files capped at 65 536 bytes; `.flf` files capped at
  1 048 576 bytes. Both checked before any glyph decode.
- Font dimensions capped: `width ≤ 64`, `height ≤ 32`, `gap ≤ 16`,
  `count ≤ 256`. Max row buffer is `256 × 32 × 64 = 524 288` bytes.
- argc capped at 256 in `main`.
- No `printf`-style format-string sites. All stdout I/O is raw
  `syscall(1, 1, ptr, len)` or println-of-literals.

### F-010 — OOM partial-failure paths leak earlier allocations &nbsp; **INFORMATIONAL**

`font_new`, `font_header_load`, and `flf_load_file` allocate in
sequence; if a later `alloc` returns 0, earlier successful allocs
are not freed before returning 0. Memory leaks in a single-shot
process that exits in milliseconds are not a security issue. Noted
for completeness; no remediation.

## External research summary

The external CVE survey (figlet, ANSI escape, hand-parsers,
TIOCGWINSZ, CLI argv→stdout) returned three actionable categories:

1. **ANSI escape injection (CWE-150)** is the bnrmr-shaped bug class.
   The Codex CLI RCE (2026) and `gh run view --log` are the closest
   precedents. → Addressed by F-001 fix + F-005/F-006/F-007 positive
   observations.
2. **Hand-parser bugs in custom font formats** — covered by the existing
   geometry caps. → Defense-in-depth via F-002 for v1.0.
3. **YAML billion-laughs class** is not reachable: bnrmr's font loader
   doesn't invoke CYML's `${...}` expansion at all, and the expansion
   primitive itself is non-recursive. → F-004 documents the contract.

The remaining survey items (TIOCGWINSZ trust, `--font` path
canonicalization, fuzzer harness, darshana terminator audit) are
captured under F-003 / F-008 / "Future work" below.

## Future work (post-0.7.0)

These are tracked recommendations, not 0.7.0 deliverables.

- **v1.0 defense-in-depth**: implement the parser-level integer cap
  (F-002) and the `ws_col ≤ 4096` clamp (F-008).
- **Fuzzer**: stand up `tests/bannermanor.fcyr` against `font_load_file`
  and `flf_load_file` with random byte streams. Hand-written parsers
  are the highest-payoff fuzz target.
- **Darshana SGR-terminator audit**: confirm `tty_sgr` / `tty_sgr_reset`
  always emit a well-formed `CSI ... m` with a final byte in `0x40-0x7E`.
  (Cross-project — file under darshana, not bnrmr.)
- **Manpage**: document the `--font foo.flf` literal-path semantics
  explicitly, alongside a "trust your font files" note.
